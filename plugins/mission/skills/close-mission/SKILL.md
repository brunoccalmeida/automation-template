Close the mission; every item is checked, not assumed. Names in backticks such as `check`, `test` and `main-branch` are **contracts**: the real command or value is in the contracts table of the project's rules (format in `${CLAUDE_PLUGIN_ROOT}/README.md`). A contract missing from the table: stop and ask the user, never guess.

1. **Gates green:** `check`, `test` and, if the project has one, `smoke` pass locally, on the branch's final state. A red gate is fixed before the reviewer, never skipped.
2. **Issues up to date:** the resolved ones cited in the PR (`Closes #N`); work discovered along the way becomes new issues labeled `priority: P0/P1/P2`, following the fields of `.github/ISSUE_TEMPLATE/`, if it exists.
3. **Session summary** (`session-summary`), on the mission branch: **state** only. A table with one idea per row (the PR queue as it will be after the merge) and the next mission recommended by the rules' priority, with links to issues and ADRs. Cite issues, not the PR number (it does not exist yet). A lasting decision becomes a rule or an ADR; a pitfall that will happen again gets a line in the summary. The history goes in the PR (step 6).
4. **README and documentation** follow what changed for whoever uses the project.
5. **Self-check, then the reviewer.** Before the reviewer, check the diff for the four author errors reviews found most often (classes in `${CLAUDE_PLUGIN_ROOT}/README.md`, "Author errors"); fix each catch and list it under **self-check** (step 6):
   - `unverified-claim`: each sentence the diff adds that says how an external tool behaves, that something ran, passed or was probed, or gives a count, cites on its line or in the PR's sources the documentation section, the run id or the command whose output shows it; an inference is worded as judgment.
   - `stale-sibling`: for each value the diff changes or removes (a path, a name, a count, a state, a label), `git grep` the old value and update every hit, or keep it with the reason in the PR; an issue body or label the change makes false is updated too.
   - `red-not-seen`: the RED record names each assertion added or changed, not each test, with the failing run or the mutation that made that assertion fail on its own; a failure behind a shared precondition (a missing file, a guard) counts for none of the assertions after it. Each gate or audit run the record relies on is there with its command and result.
   - `scope-gap`: each acceptance criterion and each explicit ask of the issue ("for each candidate…") points to the place in the diff or the PR that meets it; a sentence saying something is covered names what was run.

   Then the **reviewer** (`mission:reviewer`): save the issue text (`gh issue view <n>`) to the scratchpad and, in a second file, the branch's commit messages (`git log <main-branch>..HEAD`) followed by the summary and the full diff (`git diff --stat <main-branch>...HEAD` and `git diff <main-branch>...HEAD`); pass both paths. The messages go along because the reviewer checks the RED record in them and does not run `git`. Fix the findings that hold and run the gates again.
6. **PR with the mission record:** commit, push and `gh pr create` with `Closes #N`. The PR body **is** the record: decisions, sources consulted, how the RED was seen (or the mutation) and four lists, each with "none" when empty, because they are the raw material of the reviewer's answer key and of the author-error guards:
   - **self-check:** what step 5's self-check caught and fixed before the reviewer, and each flag it raised that was not an error, as `dismissed: <class>` with the why;
   - **fixed:** findings that held;
   - **false positives:** findings dismissed, each with the why;
   - **false negatives:** a defect the reviewer let through that its list or `REVIEW.md` covered, found after it in this mission, or coming from an earlier mission and fixed by this one or opened as a new issue (step 2). When it comes from an earlier mission, the issue that fixes it (or the PR, with no issue) gets the `reviewer-miss` label and cites the PR of the mission that delivered the defect.

   Each self-check and fixed item ends with `class: <class>; action: <action>`, both decided now. Reuse a class of the README's "Author errors" or name a new one there. The action is `guard: <what>` (a test, hook, rule or skill step this mission adds, seen failing), an issue with its priority (`#N, P2`) or `none: <why>`. Pick the guard by its cost: an error a machine can check with no exceptions gets a test or hook on its first occurrence; a judgment error gets a rule or skill step on its second, naming the class (never a generic "verify everything"); `REVIEW.md` only when nothing else fits. **Expiry:** run `gh pr list --state merged --limit 100 --json body,mergedAt --jq '[sort_by(.mergedAt) | reverse | .[] | [.body | scan("(class|dismissed): ([a-z-]+)") | join(" ")] | select(length > 0) | unique][:15] | {prs: length, counts: (add // [] | group_by(.) | map({key: .[0], value: length}) | from_entries)}'`, which counts the pull requests with each `class <name>` and `dismissed <name>`. When `prs` is 15 and a step 5 check, or a rule or skill step another mission added as a guard, has no `class` count, or more `dismissed` than `class` for its class, open an issue (`priority: P2`) in the plugin's repository to review that guard: removed if the class is no longer produced or the check is mostly noise, kept otherwise. A test or hook does not expire by absence, since it stops its class before any list sees it; one that fails a correct change is fixed or removed in the mission that sees it.

   If `.github/pull_request_template.md` exists, follow its sections (`gh pr create --body` ignores the template). Name the issues the PR closes on a line of their own (`Closes #N`, the template's first line) and, for an issue it only references, use `Refs #N` and never put a closing keyword (close, fix, resolve and their forms) next to it anywhere in the title or body, not in a negation ("does not close #N"), not in backticks: the squash writes them to the `main-branch` as a commit message, and GitHub closes the issue named after the keyword in it. Write it in words instead ("close the issue by hand", "the kit's PR will close it"). Before `gh pr create`, write the title, a blank line and the body to a scratchpad file and run `sh "${CLAUDE_PLUGIN_ROOT}/scripts/check-closing-keywords.sh" <file>`; exit 1 names each line to reword. The squash writes the body to the `main-branch` only if the repository uses the PR description as the message: check that `gh api repos/{owner}/{repo} --jq .squash_merge_commit_message` prints `PR_BODY` and, if not, warn the user before the merge. Ask the user for `/clear` and, as the **first message of the fresh chat**, `/mission:ship-pr <n>`: the skill does not need this conversation (the PR and the summary hold everything), and every call while waiting for the merge would resend the whole context. The plugin blocks `ship-pr` in a chat that already has a conversation.
7. **After the merge** there is nothing to do in this chat, which ends at step 6: `ship-pr` (step 5), in the chat that sees the merge, confirms the closed issues and the updated local `main-branch`, turns a fact that came up in the merge into an issue and says the mission is over.
